Capítulo 1

Visão geral

O Prelo guarda tudo o que importa num banco relacional: contas, endereços, catálogo, carrinhos, pedidos, pagamentos e envios. São 18 tabelas, iguais nos quatro bancos suportados. O Redis só acelera e guarda o que é passageiro.

O banco é a fonte da verdade

Estoque, preços, pedidos e pagamentos só existem no banco. O Redis guarda cache, sessões e tokens de vida curta: se ele for apagado, ninguém perde um pedido, só precisa entrar de novo. Por isso o backup do Prelo é o backup do banco.

A lista Quero ler e os livros vistos por último, que a interface ganhou nesta versão, ficam no navegador de cada pessoa (armazenamento local) e não criam tabelas nem chaves no Redis.

Como o banco é escolhido

  1. A variável DB_VENDOR ativa o perfil do Spring com o mesmo nome: application-postgresql.yml, application-mysql.yml, application-sqlserver.yml ou application-oracle.yml. Cada um só define a URL JDBC.
  2. O Hibernate detecta o dialeto pela conexão. As entidades JPA são as mesmas para todos.
  3. O Flyway lê classpath:db/migration/{vendor}: o Spring troca {vendor} pelo nome do banco conectado e roda só as migrações daquela pasta.
  4. No Docker, COMPOSE_PROFILES sobe só o contêiner do banco escolhido, sempre com o nome de rede db.

Diagrama de relacionamentos

Todas as tabelas, com chaves primárias (PK), estrangeiras (FK) e únicas (UK). Cada ligação sai da chave estrangeira, no lado muitos (pé de galinha), e chega na chave primária, no lado um (dois traços).

Só as chaves aparecem. As outras colunas estão no capítulo 3 e no capítulo 5. Um traço simples no lado do filho indica relação 1:1 (cart e shipment). coupon e shipping_method não têm chave estrangeira: o pedido copia o que valia na hora.

O diagrama da página seguinte sai de docs/fonte/diagrama-er.mmd (Mermaid). Depois de mudar o esquema, gere de novo com mmdc -i diagrama-er.mmd -o diagrama-er.png -c diagrama-er.json -s 3 -b white.

Capítulo 4

Regras da arquitetura do banco

O que toda tabela, coluna e migração do Prelo precisa seguir para continuar funcionando igual nos quatro bancos. Vale para quem for evoluir o esquema.

Nomes

  • Tabelas e colunas em inglês, snake_case, no singular (book, order_item). O Hibernate converte os campos Java (stockQuantity) para esse formato.
  • Nenhuma palavra reservada em nenhum dos quatro bancos. Por isso app_user (e não user), purchase_order (e não order), user_role, book_format, item_position, curated_catalog.
  • Restrições sempre com nome explícito e único no esquema: pk_<tabela>, fk_<tabela>_<coluna>, uk_<tabela>_<colunas>, ix_<tabela>_<colunas>. Nomes gerados pelo banco mudam de um para outro e atrapalham migrações futuras.
  • Nomes com até 30 caracteres, para caber em qualquer versão do Oracle.

Chaves e identidade

  • Toda tabela de entidade tem id numérico gerado pelo banco (GenerationType.IDENTITY). Não use sequências nem UUID gerado no banco: a identidade é o único mecanismo igual nos quatro.
  • Tabelas de ligação com ordem usam chave composta (book_id, author_order), que o JPA mantém com @OrderColumn.
  • Códigos que aparecem para pessoas (pedido, cupom, referência do pagamento) são colunas únicas separadas do id.

Booleanos

Não existe tipo booleano comum aos quatro (o Oracle só tem a partir do 23ai). Todo booleano é numérico, com 0 ou 1, e passa pelo conversor Flag (@Convert(converter = Flag.class)). Nunca crie coluna BOOLEAN, BIT ou TINYINT(1) direto.

Datas e horas

  • Momentos são java.time.Instant gravados em UTC (hibernate.jdbc.time_zone=UTC). A interface converte para o horário de Brasília na hora de mostrar.
  • Datas sem hora (previsão de entrega) são LocalDate em DATE.
  • Nunca use DEFAULT CURRENT_TIMESTAMP nem gatilhos. A aplicação preenche as datas, para o valor ser o mesmo em todos os bancos e nos testes.

Dinheiro

Valores em reais são DECIMAL(12,2) (NUMBER(12,2) no Oracle) e BigDecimal no Java, com arredondamento HALF_EVEN em duas casas. Nunca use FLOAT, DOUBLE ou MONEY.

Textos

  • Todo texto tem tamanho máximo e cabe em 4000 caracteres. Não há TEXT, CLOB ou @Lob: cada banco trata objetos grandes de um jeito, e o PostgreSQL ainda separa @Lob em outra área.
  • Unicode em todos: utf8mb4 no MySQL, NVARCHAR no SQL Server (com use_nationalized_character_data), VARCHAR2(n CHAR) no Oracle (tamanho em caracteres, não em bytes).
  • A busca sem acentos não depende de collation. A coluna book.search_text é preenchida pela aplicação já sem acentos e em minúsculas, e a busca usa LIKE sobre ela.

Integridade

  • Toda referência entre tabelas tem chave estrangeira declarada.
  • ON DELETE CASCADE só onde o filho não existe sem o pai (itens do carrinho, autores do livro, livros do catálogo, itens do pedido, eventos do envio). O resto bloqueia a exclusão, e livros saem da loja com active = 0.
  • Unicidade só em colunas NOT NULL: o SQL Server aceita um único nulo numa coluna única, os outros aceitam vários.
  • Toda chave estrangeira tem índice (o Oracle e o PostgreSQL não criam sozinhos).

Cópias no pedido

O pedido não depende de dados que mudam. Endereço, forma de envio, prazos, título, ISBN, autores e preço são copiados para purchase_order e order_item no fechamento. Mudar o endereço ou o preço de um livro não altera pedidos antigos.

Concorrência

Estoque
A reserva é um único comando UPDATE book SET stock_quantity = stock_quantity - :qtd WHERE id = :id AND stock_quantity >= :qtd. Se nenhuma linha mudar, falta estoque. Os livros são reservados em ordem de id para evitar deadlock.
Pedido
purchase_order.version (JPA @Version) impede que um pagamento e a expiração alterem o mesmo pedido ao mesmo tempo.
Pagamento
payment.idempotency_key é única: a mesma tentativa repetida devolve o pagamento já criado.

Evolução do esquema

Checklist de uma migração Mesmo número nas quatro pastas. Só tipos lógicos; nomes pk_, fk_, uk_ e ix_; índice em toda FK. Nada de BOOLEAN, LOB, FLOAT ou DEFAULT de data. Entidade atualizada e mvn verify passando nos quatro bancos.
  1. Nunca edite uma migração que já rodou em algum lugar: o Flyway confere o checksum e para a aplicação.
  2. Uma mudança é uma nova versão, com o mesmo número e o mesmo nome nas quatro pastas: V2__descricao.sql em postgresql, mysql, sqlserver e oracle.
  3. Use só os tipos lógicos da tabela acima e dê nome a toda restrição nova.
  4. Atualize a entidade JPA na mesma mudança e rode os testes. O SchemaValidationTest compara entidade e tabela no PostgreSQL e no MySQL, e o CI roda tudo nos quatro bancos.
  5. Prefira mudanças compatíveis (coluna nova aceitando nulo, depois preencher, depois exigir), para a versão anterior da API continuar funcionando durante a atualização.

Capítulo 9

Consultas úteis

SQL que roda igual nos quatro bancos, exceto onde indicado.

Pedidos por status

SELECT order_status, COUNT(*) AS pedidos, SUM(total) AS valor
FROM purchase_order
GROUP BY order_status
ORDER BY pedidos DESC;

Livros mais vendidos

SELECT b.title, SUM(i.quantity) AS unidades, SUM(i.line_total) AS receita
FROM order_item i
JOIN purchase_order o ON o.id = i.order_id
JOIN book b ON b.id = i.book_id
WHERE o.order_status <> 'CANCELED'
GROUP BY b.title
ORDER BY unidades DESC;

Para limitar a 10 linhas: LIMIT 10 no PostgreSQL e no MySQL; FETCH FIRST 10 ROWS ONLY no Oracle e no PostgreSQL; SELECT TOP 10 ou OFFSET 0 ROWS FETCH NEXT 10 ROWS ONLY no SQL Server.

Receita por forma de pagamento

SELECT p.payment_method, COUNT(*) AS pagamentos, SUM(p.amount) AS valor
FROM payment p
WHERE p.payment_status = 'APPROVED'
GROUP BY p.payment_method;

Estoque baixo

SELECT title, stock_quantity, sold_count
FROM book
WHERE active = 1 AND stock_quantity <= 5
ORDER BY stock_quantity, title;

É o mesmo critério do filtro Estoque baixo (até 5) da tela Livros e estoque na administração.

Pedidos que vão expirar

SELECT code, total, payment_due_at
FROM purchase_order
WHERE order_status = 'PENDING_PAYMENT'
ORDER BY payment_due_at;

Rastreio de um pedido

SELECT e.occurred_at, e.shipment_status, e.title, e.location
FROM shipment_event e
JOIN shipment s ON s.id = e.shipment_id
JOIN purchase_order o ON o.id = s.order_id
WHERE o.code = 'PED-DEMO2-TRANS'
ORDER BY e.occurred_at;
Capítulo 10

Como preparar o banco

Com Docker não há nada a fazer: o Compose cria banco e usuário. Para um servidor que já existe, crie um banco vazio e um usuário dono dele; o Flyway cria as tabelas na primeira subida.

PostgreSQL

CREATE USER prelo WITH PASSWORD 'troque-esta-senha';
CREATE DATABASE prelo OWNER prelo ENCODING 'UTF8';
DB_VENDOR=postgresql DB_HOST=servidor DB_PORT=5432 DB_NAME=prelo DB_USER=prelo DB_PASSWORD=...

MySQL

CREATE DATABASE prelo CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
CREATE USER 'prelo'@'%' IDENTIFIED BY 'troque-esta-senha';
GRANT ALL PRIVILEGES ON prelo.* TO 'prelo'@'%';

A URL padrão já usa UTC na sessão e aceita a chave pública do servidor (necessária para caching_sha2_password sem certificado do cliente).

SQL Server

CREATE DATABASE prelo;
CREATE LOGIN prelo WITH PASSWORD = 'Troque-Esta-Senha-1';
USE prelo;
CREATE USER prelo FOR LOGIN prelo;
ALTER ROLE db_owner ADD MEMBER prelo;

A conexão usa encrypt=true. Com certificado válido no servidor, defina DB_TRUST_CERT=false.

Oracle

-- conectado como administrador no PDB (por exemplo FREEPDB1)
CREATE USER prelo IDENTIFIED BY "troque-esta-senha" QUOTA UNLIMITED ON USERS;
GRANT CREATE SESSION, CREATE TABLE, CREATE SEQUENCE, CREATE VIEW TO prelo;
DB_VENDOR=oracle DB_HOST=servidor DB_PORT=1521 ORACLE_SERVICE=FREEPDB1 DB_USER=prelo DB_PASSWORD=...

Dar acesso de administração

UPDATE app_user SET user_role = 'ADMIN' WHERE email = 'voce@sualivraria.com.br';

A pessoa precisa sair e entrar de novo para o novo papel valer no token.
